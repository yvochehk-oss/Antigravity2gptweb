## Scope and ownership

Task15 projects a deterministic tax result at the legal-entity/month scope:

```text
(reporting_party_id, tax_period)
```

`reporting_party_id` must resolve to an active `internal_entities.party_id`
with `legal_entity = true`.  `tax_period` is the first day of a calendar month.
The Task15 tables intentionally have no `project_id`, `entity_code`, or
`invoice_date` axis:

- `entity_tax_management_inputs` — reviewed, versioned monthly `REVENUE` and
  `REAL_COST` evidence;
- `entity_tax_ledgers` — immutable deterministic result rows;
- `entity_tax_ledger_components` — exactly one typed `REVENUE`, `REAL_COST`,
  and `ESTIMATED_CIT` component for each result.

VAT is a dependency only.  Each Entity Tax Ledger must reference the official
current `entity_vat_ledgers` result for the same legal entity and month.  VAT is
not added to revenue, real cost, profit, or CIT.

## Gate behavior

The verifier is `scripts/v3/entity_tax_gate_15.py`.  It reads one PostgreSQL
`REPEATABLE READ`, `READ ONLY` transaction and performs no migration, seed,
INSERT, UPDATE, DELETE, DDL, or commit.  Its exit contract is:

- `0` — `PASS`: every physical, evidence, calculation, dependency, and formal
  pilot condition below is satisfied;
- `1` — `FAIL`: revision 87 is available, but a data or invariant condition
  fails, including the required no-pilot fail-closed condition;
- `2` — `BLOCKED`: the gate is not yet runnable, for example when the database
  remains at revision 86 and the Task15 tables do not exist.

The JSON artifact is evidence only when it is generated against the named
database and its status, exit code, heads, schema, and data evidence are
preserved.

## Final PASS contract

Gate S15 may be marked PASS only when all of the following are true:

1. The PostgreSQL tax head and migration disk head are both exactly
   `87_v3_entity_tax_ledgers`.

2. All three revision-87 tables exist with the required indexes, foreign keys,
   unique constraints, named checks, and all eight enabled protection triggers.
   The physical schema contains none of `project_id`, `entity_code`, or
   `invoice_date` in the Task15 tables.  The strict shared Tax/RAG schema audit
   returns PASS with no failures or warnings; a tax-only fixture is not enough.

3. Every official ledger row is in an active legal-entity scope.  Its
   `CalculationRun` is a SUCCEEDED `ENTITY_TAX` run with the same party and
   month, and `TaxPeriodState(tax_type = 'ENTITY_TAX').current_run_id` points to
   that result.

4. The referenced VAT result is official and current for the exact same scope:
   the VAT period state points to a SUCCEEDED VAT run, that run has exactly one
   matching `EntityVatLedger`, and `entity_vat_ledger_id` points to it.

5. The scope contains reviewed, explicit-month `REVENUE` and `REAL_COST`
   inputs.  Each has a nonnegative amount, positive version, nonblank source,
   review identity and review time, and the stored first-of-month period.  For
   each type, the highest version in the exact party/month scope is selected.
   A higher unreviewed, ambiguous, malformed, or otherwise unavailable input
   fails closed; it cannot be silently ignored.

6. Exactly one requested CIT rule (normally `CIT_GENERAL`) is reviewed and
   effective for the month.  The rate must come from that explicit `tax_rules`
   row.  There is no inferred or default rate; missing, ineffective,
   unreviewed, ambiguous, or malformed rule evidence fails closed.

7. Every stored result recomputes under the fixed ruleset
   `V3_ENTITY_TAX_LEDGER_V1`:

   ```text
   revenue          = selected reviewed REVENUE amount
   real_cost        = selected reviewed REAL_COST amount
   estimated_profit = revenue - real_cost
   estimated_cit    = max(estimated_profit, 0) * effective CIT rate
   ```

   Monetary values are normalized to two decimal places with
   `ROUND_HALF_UP`.  A loss therefore has zero estimated CIT; VAT remains
   outside this formula.

8. The canonical input and result payloads are SHA-256 bound.  The hashes in
   `calculation_runs` and `entity_tax_ledgers` match the deterministic domain
   calculation and each other.

9. Each result has exactly three components, one each of `REVENUE`, `REAL_COST`,
   and `ESTIMATED_CIT`.  The component amounts reconcile to the ledger totals;
   the first two point to the selected management inputs and the CIT component
   has no management-input source.

10. An `OPEN` period has a current STANDARD result with no supersession.  A
    `CLOSED` period has a SUCCEEDED STANDARD close anchor and a direct,
    acyclic chain of SUCCEEDED `RESTATEMENT` runs.  Historical ledgers remain
    immutable and retained; a result is never patched in place.

11. At least one valid formal legal-entity/month pilot exists in the target
    PostgreSQL database.  An empty `entity_tax_management_inputs` table or an
    empty `entity_tax_ledgers` table means unavailable evidence, not a zero
    result, and cannot pass the gate.

12. The required PostgreSQL regression evidence and formal Gate/strict-audit
    artifacts for the current Task15 tree are available.  Independent
    `final_reviewer` acceptance is a separate final-release condition and is
    currently pending; this Gate PASS must not be presented as a reviewer PASS.

## Simulation and fail-closed boundary

The following actions cannot satisfy Gate S15:

- inserting `0.00` management inputs or a zero ledger merely to make a table
  non-empty;
- using an unreviewed, guessed, or default CIT rate;
- deriving the monthly revenue or cost period from invoice dates or project
  rows;
- copying an unreviewed Task14 or Task15 fixture into the formal database as if
  it were reviewed source evidence.  The named, user-authorized A08 simulation
  package is accepted only as explicitly reviewed simulation evidence for this
  test project;
- treating VAT totals as revenue, real cost, profit, or CIT;
- bypassing the PLAN/APPLY transaction, hashes, foreign keys, checks, or
  protection triggers;
- treating green unit tests, a migration file on disk, or a successful SQL
  restore as a formal pilot or production PASS.

A clearly labelled, user-authorized synthetic fixture may be used to exercise
the pipeline in an isolated validation database.  For this project, the
explicitly reviewed A08 / 2025-09 simulation package is also the formal Gate
S15 pilot; that acceptance is limited to the authorized simulation test and
does not turn the material into a real business financial statement, accounting
record, tax return, or external proof.
