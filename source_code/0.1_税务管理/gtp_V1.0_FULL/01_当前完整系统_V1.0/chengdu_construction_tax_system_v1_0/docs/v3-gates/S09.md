## Validation semantics

Task09 is deliberately three-state and evidence-aware:

- deterministic contradiction -> `INVALID`;
- missing/ambiguous evidence -> `NEEDS_REVIEW`;
- only complete deterministic evidence -> `VALID`.

`DIGITAL_V1` and `LEGACY_V1` reuse the Task07a physical-invoice identity
contracts. `LEGACY_MIGRATION_V1` is migration provenance only and may not be
promoted directly to `VALID`.

Tax rates are not hard-coded. A reviewed/versioned manifest may be supplied in
PLAN mode. If invoice lines exist and no reviewed rate context is bound, the
validator fails closed to `NEEDS_REVIEW`. The manifest template is:

`docs/v3/invoice_tax_rate_rules.template.json`

Do not change the template to `reviewed: true` merely to pass the Gate. Create a
separate reviewed evidence file only after the Tax owner has approved its
`rule_version`, source and allowed-rate set.

### 5. Apply the exact saved plan

```bash

  --plan v3_invoice_validation_plan.json \

  --confirm-database projectrag \
  --json v3_invoice_validation_result.json
```

APPLY may update only `facts.validation_status` plus audit evidence. It must not
