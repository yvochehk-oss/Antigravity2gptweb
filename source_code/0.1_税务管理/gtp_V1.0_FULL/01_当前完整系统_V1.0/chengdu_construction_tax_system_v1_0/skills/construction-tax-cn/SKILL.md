# construction-tax-cn

## 主体
系统内：A施工、B劳务、C商贸、D设备租赁。
系统外：甲劳务、乙设备、丙材料、丁专业分包/其他。

## 两套口径
1. 项目综合经营：抵消ABCD内部交易，穿透真实底层成本。
2. 法人独立经营/税务：ABCD分别按自身账面业务计算，不使用合并抵消结果代替法人税务。

## 强制规则
- 甲乙丙丁只作为外部成本、发票、资金、履约和风险变量。
- 税额必须来自确定性计算引擎。
- 税务规则未复核时必须提示。
- 不得建议虚构劳务、虚构采购、虚假设备租赁、购买发票、资金空转或其他无真实业务安排。
- 分析四流时必须同时检查合同、履约、发票、付款。

## 外部模型审查
当用户请求检查某个项目环节或整个项目时：
1. 先读取本地确定性计算结果和四流/风险数据。
2. 按用户要求选择审查 scope。
3. 仅构造该 scope 所需的最小项目上下文。
4. 外部模型只能解释、审查和建议，不得覆盖本地税额、利润和 EAC 结果。
5. 保存模型、scope、用户指令、输入摘要、结果和原始响应，确保可追溯。
6. AI 返回非严格 JSON 时，必须在 Job 上标记 parse_failed 并由人工审阅原始响应。

## V0.2 项目体检与整改闭环
当用户要求"全面检查项目""项目体检""多模型复核"时：
1. 创建项目体检 Batch，不用一个超大 Prompt 直接塞全部数据。
2. 按 quick/standard/deep 拆分多个 Scope。
3. 每个 Scope 先运行本地确定性计算，再调用选定模型。
4. 多模型结果由本地共识引擎汇总，共同发现和差异意见分开显示。
5. Scope × Endpoint 任务并行执行（线程池），不再串行阻塞 Web。
6. AI 建议只有在用户确认后才转成 RemediationTask。
7. 整改完成后创建新的复检 Job，保留 parent_job_id 和 recheck_job_id。
8. AI 不能自动把整改任务标记为 verified/closed，最终确认由用户完成。
9. 每次检查记录实际使用的 Prompt 版本，保证可追溯。
10. 风险阈值由 RiskThreshold 表驱动，业务侧可调；未配置时回退到代码默认。
